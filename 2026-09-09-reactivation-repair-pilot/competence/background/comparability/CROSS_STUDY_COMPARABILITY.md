It records a descriptive comparison made while the new program continued; it is not a factorial validation result or a causal explanation of the difference. ## What is unchanged in the compared stages

**Loss and optimizer.** The [old training loop](support/source_excerpts.md#old_uniform_training), lines 63–71, sums target-token counts over all 16 examples before processing microbatches of 8, then backpropagates `losses.sum() / target_count` for each microbatch. Their accumulated gradient is the full effective-batch token mean. The [new loop](ADDITIONAL_SOURCE_EXCERPTS.md#new_training_loop), lines 76–85, uses the same grouping; [objective.py](support/source_excerpts.md#new_class_weights_and_uniform_reduction), lines 9–34, assigns every uniform example weight 1.0, sums the entire group's weighted token count, and explicitly preserves the flat `losses.sum() / denominator` operation. The denominator is now an integer-valued Python float rather than an integer; that bookkeeping change does not change this mathematical objective. This review does not claim independently demonstrated bitwise GPU equivalence.

Both instantiate a fresh AdamW optimizer each epoch, with learning rate 0.0001, weight decay 0, no warmup, and gradient clipping at norm 1.0. Adapter weights carry between epochs; optimizer state does not. See old loop lines 48–80 and new loop lines 59–94. Training seeds are 1729, 1730, and 1731 in both, and all three saved index permutations are identical when mapped back to each study's source-file positions. Each epoch makes 96 updates over all 1,536 examples: 288 updates and 4,608 example presentations per completed chain. Both record 29,933,568 trainable parameters and a maximum encoded sequence length of 553. The realized target-token budget is **65,417 per epoch old versus 65,378 new**; prefix tokens are 760,323 per epoch in both. Equal update budgets therefore do not mean identical target-token totals.

**Complete prompt and answer construction.** The [old message builder](support/source_excerpts.md#old_message_construction), lines 17–21, and [new builder](support/source_excerpts.md#new_message_construction), lines 19–23, construct the same system/user pair. The byte-identical [common.py](support/source_excerpts.md#old_chat_encoding_loss_and_generation), lines 14 and 55–70, supplies the system message, tokenizer chat template, target/EOS encoding, and causal labels. The inherited [task renderer](support/source_excerpts.md#old_complete_user_prompt_renderer), lines 249–294, already contains “Prefer that order with decision first”; this is not a new instruction. [serialization.py](support/source_excerpts.md#new_answer_order_and_unchanged_first_prompt), lines 80–85, returns that exact renderer output for `decision_first`. Its extra output-order and source-hash metadata are not inserted into the messages. All 3,456 competence/calibration source rows across the two studies were checked: regenerated decision-first prompts and supplied targets equal their stored strings exactly. None uses a custom `messages` field.

**Model, precision, and generation.** The configuration, common model code, task oracle, narrative renderer, and GPU startup wrapper are byte-identical. Both use the pinned Qwen2.5-3B-Instruct revision, rank-16/alpha-32 LoRA with zero dropout, NF4 double quantization with bfloat16 computation, SDPA, and the same frozen-weight preparation in training and evaluation. Left padding, attention masks, absolute training position IDs, float32 cross-entropy logits, non-reentrant gradient checkpointing, and the 24 GiB allocator cap are unchanged ([common.py](support/source_excerpts.md#old_chat_encoding_loss_and_generation), lines 25–109). The old [base-model identity inventory](support/source_identities.json) and new [freeze](support/source_identities.json) record identical hashes for all 11 model/tokenizer files; large weight files were not reread for this review.

Every compared calibration contract specifies greedy generation, batch size 16, seed 90210, and a 192-token cap. **Both old and new calibration have `score_decision=false`.** Old supplemental canonical-prefix scoring was reserved for the conditional held-out stages that never ran; the new program disables it globally. There was no removed scoring forward pass in these compared calibration stages, and no scoring-related RNG or state explanation is supported by these records.

The [allowlisted runtime comparison](support/source_identities.json) records matching research-image provenance while omitting operational image identifiers and private records. The new recorded versions are Python 3.12.3, Torch 2.13.0+cu130, Transformers 5.12.1, PEFT 0.18.1, and bitsandbytes 0.49.2. No separate old machine-readable package-version inventory was found. Shared image provenance is stronger evidence here than an independently verified old/new package listing; neither establishes bitwise runtime identity or a demonstrated rebuild of the private GPU environment.

## Substantive design and provenance differences

Fresh training and calibration facts include changed source order, eligible-count distributions, and joint assignments of domain/pressure to policies. Both retain identical family × threshold × stratum counts and the same marginal domain and pressure/oversight counts. The [new generator](ADDITIONAL_SOURCE_EXCERPTS.md#new_split_generation), lines 266–302, uses separate split seeds starting at 202609101, compared with the old generator's continuous development RNG starting at 20260910. It also excludes all 6,592 prior semantic cases and adds an independent 384-case validation set. The case-construction rules and authoritative oracle are inherited. “Fresh facts” therefore does not imply that the two realized datasets have identical difficulty.

The [old driver](support/source_excerpts.md#old_calibration_arguments_and_first_passing_selection), lines 195–216, would accept the first passing competence epoch and stopped the program after seed 1729 failed all three. The [new driver](support/source_excerpts.md#new_fixed_three_epoch_selection_and_validation), lines 149–196, always trains all three epochs for all four recipes and both seeds, selects only from epoch-3 calibration under fixed priority, and requires fresh validation of the selected recipe without fallback. The new first-seed uniform-first chain already passed at epoch 2 but continued as specified. This is a substantive selection and reporting change, although the epoch-3 comparison above has the same realized update budget. New weighting/serialization dispatch, class-token accounting, and rendered-row hash contracts extend provenance; they do not introduce either factorial intervention into this uniform-first chain.

Recommended final-report caveat:

> For the first optimization seed, 1729, the uniform, decision-first control passed calibration on the fresh training/calibration allocation, although the preceding study's first-seed control did not. This statement does not mean that the uniform-first recipe passed in both seeds. Both used the same whole-effective-batch target-token objective, optimizer and seed schedule, model precision, prompt contract, and generation settings. Because the facts and development procedure changed between studies, this difference does not identify a cause or measure the benefit of class reweighting or decision-last serialization. Those intervention claims depend on the new study's paired factorial validation, not this cross-study comparison.

The completed [training and calibration review](../../results/training_execution_review/REVIEW.md) covers both optimization seeds. The second uniform-first seed, 2718, failed the epoch-3 CLEAR-control gate, so the uniform-first recipe did not qualify for the shared two-seed selection. The fixed priority selected `weighted_first` among eligible recipes. These are calibration/selection facts; this document contains no validation effect estimates. The exact [selection and gate evidence](../../results/training_execution_review/RESULT.json) supports that distinction.
